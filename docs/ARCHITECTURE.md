# 架构与邮箱生命周期

## 为什么只做收信

当前业务只需要接收邮件验证码和预约确认信，不需要用客户邮箱发信。Cloudflare Email Routing 接管域名入站 MX，Email Worker 把邮件原文保存下来；网页收件箱提供独立的登录能力。这个地址能真实收信，但不是可通过 IMAP/POP3 登录的传统邮箱。

Catch-all 只配置一条路由。每次创建邮箱是在 D1 中增加记录，Worker 收到邮件后按收件地址查询；未知、停用或过期的地址调用 `setReject()`。Cloudflare 当前每个域名的路由规则数量有限，逐客户创建路由不适合本业务。

## 数据模型

| 表/存储 | 内容 | 关键约束 |
|---|---|---|
| `mailboxes` | 订单 ID、地址、密码摘要、状态、到期和清理时间 | `external_id` 与 `address` 唯一 |
| `messages` | 邮件元数据、R2 对象键、收到时间 | 只能关联一个邮箱；按 `Message-ID` 尽量去重 |
| `sessions` | 不可逆的会话令牌摘要、邮箱 ID、会话到期 | 每次读信都会重新检查邮箱状态 |
| R2 | 完整 `.eml` 原文，包含邮件头及 MIME 正文 | 私有桶，不提供公开对象 URL |

`externalId` 应使用原平台稳定的订单 ID，不要使用客户姓名或手机号。地址采用随机本地部分，避免暴露客户身份与订单号。

## 生命周期

```text
创建地址（可收信、无客户密码）
  → 抢票程序提交地址、通过管理 API 读取验证码
  → 预约成功后签发客户密码（只返回一次）
  → 客户网页登录看确认信
  → 到达 expiresAt：登录、读信、收信立即失效
  → 到达 purgeAt：Cron 删除 R2 原文、D1 邮件、会话和邮箱记录
```

创建请求必须明确传入带时区的 `expiresAt`，例如 `2026-12-01T12:00:00+09:00`。服务转换为 UTC 保存，避免东京/上海时区混淆。`purgeAt = expiresAt + PURGE_GRACE_HOURS`；默认清理宽限为 48 小时。宽限期间客户已无法访问或收信，仅为处理误操作、投递异常和清理重试留出时间。若需要立即物理清理，可设宽限为 0，但仍取决于 Cron 下一次运行。

停用接口会立即改变状态、删除会话并将 `purgeAt` 改为当前时间。Cron 每小时运行一次，每轮最多处理 20 个邮箱、每邮箱最多 100 封邮件；积压时下一轮继续。服务端请求检查不依赖 Cron，因此清理延迟不会延长客户访问权限。

## 邮件读取

入站 Worker 先核对地址和大小上限，再把原始字节写入 R2，最后把元数据写入 D1；D1 写失败时尝试删除已写的 R2 对象并拒收邮件。读验证码时要求调用方提供 `since`，只查看该订单本次预约开始之后的近期邮件，避免拿到旧验证码。

MIME 解析支持常见的 `multipart`、`base64`、`quoted-printable` 和日文常见字符集。客户页面默认只显示纯文本内容，原始邮件可下载为 `.eml`。HTML 邮件会被提取为文本，**不会在主页面运行发件人提供的 HTML/脚本**。若现场要求完整 HTML 版式，需要在上线验收时确认，并另行加入隔离的 HTML 预览。

## 对外依赖与边界

- DNS 与 MX：域名必须能由 Cloudflare Email Routing 接收；不要在已运行其他邮箱服务的同一域名上直接覆盖 MX。
- Cloudflare：Email Routing、Workers、D1、R2、Cron。免费档有请求、CPU、存储与大小限制；应在 Cloudflare 控制台设置用量告警。
- 宝可梦站点：必须实测自有域名能收到验证码和确认信，且延迟满足预约过程。不同平台可能拒绝新域名或要求手机号，邮箱服务本身无法解决这些限制。
- 客户：收到密码后可以阅读、截图或下载邮件；到期停用只能撤销服务端访问，无法撤回客户已经保存的副本。
